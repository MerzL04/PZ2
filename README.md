# Учебный проект: Настройка CI/CD с помощью GitHub Actions

Этот репозиторий создан в рамках лабораторной работы по настройке системы непрерывной интеграции (CI) и непрерывной доставки (CD) с использованием GitHub Actions.

## 📌 Описание проекта
Проект демонстрирует базовый пайплайн CI, который автоматически запускается при изменении кода. Включает в себя настроенные unit-тесты, защиту основной ветки и процесс релиза.

## 🚀 Технологии и инструменты
*   **Система контроля версий:** Git, GitHub
*   **CI/CD:** GitHub Actions
*   **Язык тестирования:** Bash / Python (в зависимости от выбранного скрипта)

## 🌿 Стратегия ветвления (Git Flow)
В проекте используются следующие ветки:
*   `main` — основная ветка. Сюда попадает только стабильный, протестированный код.
*   `development` — ветка для разработки новых функций и исправления багов.
*   `release/*` — ветки для подготовки к выпуску новой версии.

## ⚙️ Как работает CI (Непрерывная интеграция)
Файл конфигурации находится по пути `.github/workflows/main.yml`. 

**Пайплайн автоматически запускается при:**
1. Любом пуше (коммите) в ветки `main`, `development` и `release/*`.
2. Создании или обновлении Pull Request (PR), направленного в ветки `main` или `development`.

**Что делает пайплайн:**
1. Запускает виртуальную машину на Ubuntu (`ubuntu-latest`).
2. Клонирует код из репозитория (`actions/checkout`).
3. Запускает скрипт с тестами (`bash test.sh`).

Если все тесты проходят успешно, шаг загорается зеленым. Если хотя бы один тест падает — сборка останавливается с ошибкой (красный крестик).

## 🛡️ Защита ветвей и Auto-merge
*   В настройках репозитория (Branch Protection) включено правило **Require status checks to pass before merging**. Это запрещает вливать код в `main`, если тесты CI не прошли.
*   Настроено **Auto-merge**. Как только Pull Request получает одобрение и все тесты пройдены, изменения автоматически вливаются в основную ветку.

## 🏷️ Процесс релиза
1. Создается ветка `release/vX.X.X` из `main`.
2. Вносятся финальные правки и обновляется документация.
3. После успешного прохождения CI создается тег версии (например, `v1.0.0`) и публикуется GitHub Release.
